What “done” means
The same tables, relationships, and delete rules exist. The same public and admin routes answer with the same headers, filters, and
JSON envelope. Bad category and asset writes are rejected for the same reasons. A fresh database can be seeded, and a staff user can
be created from environment variables.
How to use this guide
This is the design of the AssetVerse backend. It is the spec you are matching. Build the service yourself from these flows,
diagrams, and rules. When your result and this guide disagree, change your result.
Work in this order
 · Product and architecture. Learn what the service is for and which process owns which job.
· Flows. Follow one public read, one device login, and one publish action from the client to the database.
· Relationship map and database diagrams. Draw the tables before you write endpoints.
· API catalog. Match paths, headers, query parameters, and field names. Mobile clients already depend on them.
· Implementation plan. Build one phase at a time and tick the checklist at the end.

How to use the existing repository
The repository is a reference implementation, not a file to copy. Use it when a rule in this guide is ambiguous. Do not start by cloning
view files into a new project. Start from the diagrams.
The product
AssetVerse is the content API for TeraFort photo and video editor apps. One backend serves more than one mobile app. Each
app is a row in App Setting, identified by a slug. The seeded app is ai_photo_infinity (AI Photo Editor Infinity).
Editors publish the catalog. The phone reads it. The phone does not create frames, stickers, or categories.

The same child slot is reused for stickers, effects, slides, and fonts. One child holds one variant.
A parent category is a block on the home screen: title, cover, orientation, and an optional listing section. A child category is a
collection of one asset kind. Assets hang off the child, never off the parent.

Envelope
status, data, message
· CORS, then the Django stack. Security, WhiteNoise, session, common, CSRF, auth, messages, clickjacking.
· Authentication is optional per view. The defaults try a staff DRF token, a session cookie, then a public device token.
Public catalog views clear that list.
· Permission runs next. The project default is “authenticated”. Public catalog views replace it with the API key. Admin
views require a staff user.
· The queryset hides other apps. Public lists also keep only rows whose status code is active.
· Serializers speak in codes. Clients send portrait or active, not lookup UUIDs. Category and asset ids stay UUIDs.
· Errors use the same envelope. The message is the validation detail. data is an empty object.
Lists are not paged
The base viewset can wrap a page, and no pagination class is configured. A list response puts the whole array in data. Keep it that way
until a client asks for pages.

Token rules
 · The key is 32 hex characters from a UUID. The column allows 40.
· One device user has one token. Login deletes the previous row, then inserts the new key.
· A later call with Authorization: PublicToken <key> also sends X-App-Name.
· Reject the token when the user is inactive, or when the stored app name differs from the header.
· Public catalog routes ignore this token. They require the API key.
app_name is a string, not a foreign key
Public User stores the app slug in a char field. The unique key is (device_id, app_name). The header is still checked against App
Setting. Renaming a slug does not rewrite old device rows, so those tokens stop matching until the stored app name matches the
header.

Content-Type: application/json

App scoping
X-App-Name

App Setting

Public filters follow
this chain. Assets
inherit the app from

· Every public catalog view reads X-App-Name and requires an active App Setting with that slug.
· Categories store app_id. Assets do not. An asset belongs to an app because its category does.
· Public category queries filter app__slug and status__code = active.
· Public asset queries filter category__app__slug and the asset’s own active status.
· An asset list does not also require the category’s status to be active.
· Deleting an app setting is blocked while any category points at it.
Content rules
Enforce these rules in model validation and again in the write serializer. Admin forms and the JSON API must both fail the
same way.

Frame write details the other assets do not share
 · The frame body may include a constraints array (value_1 through value_4, plus sort_order). The server stores the
numbers and does not interpret them.
· On update, a present constraints array deletes the old rows and inserts the new ones. An omitted array leaves the old
rows in place.
· Layer images are not inside the frame body. They are rows on /api/home-assets/admin/frame-assets/, each pointing at a
frame and a frame-key code.
· Tags on frames, stickers, effects, and fonts are a list of tag codes. Any active tag is allowed. Omitted tags on update stay
as they are. An empty list clears them.
· Slides have no tags.

Public query parameters

File storage
Models store a path. The storage backend turns that path into a URL. With AWS_STORAGE_BUCKET_NAME set, the backend is S3:
public objects, no query-string signature, cache for one day. A custom domain, when set, is the public host. Without a bucket,
files land in the media folder and are served only when DEBUG is on.

Implementation plan
Build in this order. Finish the check before starting the next phase. Each phase is small enough to review.
1
Service shell
Build. Django project, PostgreSQL settings from the environment, CORS headers, the JSON envelope, and the exception
handler.
Check. GET /health/ returns the envelope and does not query the database. A bad request returns the same envelope with
an empty data object.
2
Staff access
Build. Email user with a UUID primary key, Unfold admin, and the ensure_superuser command.
Check. ADMIN_EMAIL can open /admin/. A second container start does not create a duplicate user.
3
Apps and lookups
Build. App Setting, the shared lookup columns, Tag with its six types, and seed_data from JSON.
Check. Running the seed twice updates labels and does not duplicate codes. Inactive lookups exist and are hidden from
write lookups.
4
Categories
Build. Two-level tree, public GET, admin CRUD, cover upload, and the validation rules.
Check. A grandchild is rejected. A child cannot move under another app. tag must be availability and section must be listing.
5
Frames
Build. Frame, constraints, frame assets, upload paths, public list, and both admin routes.
Check. A frame on a root or on a sticker category is rejected. Sending constraints on update replaces the old rows.
6
The other assets
Build. Sticker, effect, slide, and font, each with the matching variant rule. Fonts accept ttf only.
Check. Each public list requires the API key and the app header, and returns only active rows for that app.
7
Device users
Build. Public user, one-token rotation, PublicToken authentication, and the lookup bundle.
Check. A second login invalidates the first key. A token issued for app A fails when the header is app B.
